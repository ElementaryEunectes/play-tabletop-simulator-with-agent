# I18N.md —— 给一款**外文 mod** 做本地化（机翻）时读我

> **什么时候读我**：你想让中文玩家直接玩一款英文/日文工坊 mod 的时候。**读这一次就够了**（不是每回合）。
> ⭐ **本仓库不内置任何翻译引擎** —— 它只提供**接口**，引擎你自己挂（本地引擎 / 手工 / 云都行）。外部候选 ⇒ `PRIOR_ART.md` §9.3；工具清单 ⇒ `MAINTENANCE.md` §5。

## 0. 架构：中间那段是你的，两端是我们的（**两端都已实现**）

```
Saves\TS_AutoSave*.json                  ← 游戏写出来的自动存档（只读它）
        │  tts\tools\i18n_export.ps1     读存档 · 抽文本字段
        ▼
text.tsv        id <TAB> field <TAB> source     ← ⭐ 接口就在这个文件
        │  【翻译】你的引擎 / 手工 / 任何东西
        ▼
text.zh.tsv     id <TAB> field <TAB> target
        │  tts\tools\i18n_apply.ps1      按 id 配对 · 写前校验 · 字节级替换 · 回读校验
        ▼
patched.json    → 放回 Saves\ → 在 TTS 里 Save & Load
```

```powershell
# ① 导出（不给 -Save 就用 Saves\ 里最新的自动存档；不给 -Out 就写 cache\i18n_text.tsv）
powershell -NoProfile -ExecutionPolicy Bypass -File tts\tools\i18n_export.ps1 -Save <save.json> -Out text.tsv

# ② 翻译：把第 4 列填上（能读 TSV / 写 TSV 的任何东西都行），见 §2

# ③ 回写（⛔ 默认只报告，加 -Apply 才真的写）
powershell -NoProfile -ExecutionPolicy Bypass -File tts\tools\i18n_apply.ps1 -Save <save.json> -In text.tsv -Out patched.json -Apply
```

### 接口契约（唯一的约定）

**翻译器 = 吃 TSV、吐 TSV、只填最后一列。**

- **输入**列：`id` · `field` · `source` —— `field` 只是给人看的提示
- **输出**列：`id` · `field` · `target`。**`id` 必须原样**（对应存档里第几个匹配）；`target` 留空 ⇒ 该条保持原文
- **顺序无所谓**：回写**按 `id` 配对**，不按行序 —— 翻译器可以重排、可以只回一部分行
- **值里的 tab / 换行写成 `\t` / `\n`**（`\` 本身写成 `\\`）：这是 TSV 的显示层转义，两侧对称，翻译器只需**原样保留**你不改的部分
- **空值也有行**（真实存档里约四分之三的字段是空串）：不导出它们会让后面的 id 整体错位、把译文配到**别的卡**上
- 为什么是 TSV 不是 JSON：**可 diff、可人工编辑、可流式**，而翻译引擎基本都不是 PowerShell

## 2. 部署矩阵：引擎怎么选（**按本机可行性排序**）

| 方案 | 依赖 | 离线 | 说明 |
|---|---|---|---|
| ⭐ **Transformers.js**（`@xenova/transformers`） | **只要 Node** | ✅ 模型首次下载后 | 与本仓库现有运行时一致（本来就只有 Node ＋ PowerShell）· 例 `Xenova/nllb-200-distilled-600M`（多语）或 `Xenova/opus-mt-en-zh` · CPU 能跑 |
| **Argos Translate** | Python | ✅ | 质量稳 · 模型约 100 MB/语对 · 有 CLI · 批量快 |
| **LibreTranslate** | Python 或 Docker | ✅ | 带 HTTP API（多进程友好）；Argos 的上层封装 |
| **本地 LLM**（ollama 等） | 独立运行时 | ✅ | 质量最高，**而且仍然零 token**（本地推理）；要 GPU 才快 |
| 手工 / 半自动 | 无 | — | 直接给人编 TSV —— 这本身就是一个"可用选项" |
| ❌ 云翻译 API / 大模型逐条翻 | 网络 ＋ 计费 | ❌ | **与"省 token"直接冲突** ⇒ 不作为默认路径 |

⚠️ **本机实测现状（2026-10-13）**：这台机器**只有 Node**（`python` 是 Microsoft Store 的假 stub，没有 pip / docker / ollama / tesseract）⇒ **上表只有"依赖存不存在"是实测的，配方本身尚未在本机跑过**。
**一条命令就能验证那条首选路线**（在你那台能出网的终端跑）：

```powershell
npm i @xenova/transformers
node -e "const {pipeline}=require('@xenova/transformers');pipeline('translation','Xenova/opus-mt-en-zh').then(async t=>console.log((await t('Draw two cards.')).translation))"
```

出中文 ⇒ 这条路通。**把它包成"吃 TSV 吐 TSV"的小脚本就接上了** —— 形状如下（⚠️ **本沙箱装不了 npm 包，所以这段是"照抄的样板"而不是已测过的成品**；它只做三件事：读表、翻 `source` 列、把结果写进 `target` 列）：

```js
// tsv-translate.mjs - a translator that satisfies the contract: read TSV, write TSV, fill column 4.
//   node tsv-translate.mjs text.tsv text.zh.tsv
import fs from 'node:fs';
import { pipeline } from '@xenova/transformers';

const [inPath, outPath] = process.argv.slice(2);
const translator = await pipeline('translation', 'Xenova/opus-mt-en-zh');
const esc = (s) => s.replace(/\\/g, '\\\\').replace(/\t/g, '\\t').replace(/\r/g, '\\r').replace(/\n/g, '\\n');

const out = [];
for (const line of fs.readFileSync(inPath, 'utf8').split(/\r?\n/)) {
  const cols = line.split('\t');
  if (cols.length < 3 || line.startsWith('#')) { out.push(line); continue; }   // comments + header
  const [id, field, source] = cols;
  if (!source) { out.push([id, field, source, ''].join('\t')); continue; }     // empty stays empty
  const res = await translator(source);
  out.push([id, field, source, esc(res[0].translation_text)].join('\t'));
}
fs.writeFileSync(outPath, out.join('\n'), 'utf8');
console.log('wrote ' + outPath + ' (' + out.length + ' lines)');
```

其余引擎同理：**只要它最后能产出一张"前三列原样、第四列是译文"的 TSV**，本仓库这一侧不需要知道它是谁。手工翻译就直接用编辑器填第四列。

## 3. 为什么这样切（取舍，都是付过代价的）

- **引擎不进仓库**：体积大、语对多、更新快；绑进来等于让本仓库变成它们的发行版。我们只出**两端不依赖引擎的脚本** ＋ **一个文本接口**。
- ⛔ **绝不重新序列化整个存档**（2026-10-12 实测）：`JavaScriptSerializer` 会把字段丢掉/乱序 ⇒ **静默毁存档**。所以回写是**字节级替换**（只换值那一段、从文件末尾往回换），改完**回读校验**产物仍是合法存档 JSON。
- **写前先校验，不信顺序**：回写会拿 TSV 逐条与**重新扫描的存档**比对（字段名 + 原文），对不上就是"存档在导出后被改过 / TSV 被手改过" ⇒ **拒绝**（`exit 3`），并打印前几条差异。要硬来才用 `-Force`。
- **默认不写、不覆盖输入**：不带 `-Apply` 只报告会改几条；`-Out` 指向输入存档时要求显式 `-Force`。工具**从不碰 `Saves\`**，放回去是你的决定。
- **不需要重烤、不碰桥接**：本方案只改文本字段，与 `lua\dsh_global.lua` 无关。
- **机制在库、开关在工具**：机制住在 `tts\lib\i18n.ps1`（无 `exit`、不碰文件），两个工具只做参数与 I/O，测试**直接调函数**而不 spawn 子 PowerShell（沙箱会拦 `powershell.exe` 后代）。

## 4. 测到什么程度了（**要写"可用"之前先看这段**）

离线门禁 `tts\tests\test_i18n.ps1`（`run_all.ps1` 的第 7 条，不需要 TTS）覆盖 16 个用例，其中包括**两个阴性对照**：

- 转义往返（引号 / 反斜杠 / 换行 / tab）· 一个形如真实存档的 fixture 扫出预期行数
- ⭐ **重复值按 `id` 配对而不是按值配对** —— 两张同名卡必须各拿各的译文（这是本机制最危险的失效模式）
- 不在字段表里的东西（`Name` · `TurnOrder` · `VersionNumber`）**原样留存** · 产物**重新解析仍是合法存档**
- ⛔ **阴性对照 1**：存档在导出后被改过 ⇒ **拒绝**且一个字节都不动
- ⛔ **阴性对照 2**：TSV 缺行 ⇒ **拒绝**
- `-Force` 确实能越过拒绝（逃生门本身也被测了）

⚠️ **仍未验**（要 TTS ＋ 人）：把 `patched.json` 放进 `Saves\` 后 **TTS 能不能正常载入**、字体会不会缺字。本方案的每一步都只改文本，但"改过的存档被游戏接受"这件事只能在游戏里证实 —— 与 `VALIDATION.md` 里其它待验项同一性质。
